# CLAUDE.md — NestJS app

Per-app context. Inherits monorepo conventions from the root `CLAUDE.md`; this file
covers only what is specific to a NestJS app.

## Stack

- NestJS 11 (Express 5 platform), TypeScript (CommonJS output via `nest build` → `build/`).
- Swagger at `/api/swagger` (`@nestjs/swagger`), config via `@nestjs/config` + dotenv.
- Validation: `class-validator`. Tests: **vitest** (`vitest.config.mjs`).

## Layout

- `src/main.ts` — bootstrap (Nest factory, port from `ConfigService`).
- `src/app.setup.ts` — `configureApp(app)`: global prefix `api`, `cookie-parser`, `ValidationPipe`, shutdown hooks. Shared with tests.
- `src/swagger.setup.ts` — `buildSwaggerDocument` / `setupSwagger` (bearer auth as a global requirement that `@Public()` clears per operation, UI at `/api/swagger`).
- `src/modules/health/` — `GET /api/health` (`@nestjs/terminus`, DB check via `PrismaHealthIndicator`).
- `src/app.module.ts` — root module; register domain modules here (imported from their `index.ts`).
- Domains in `src/modules/{core,transactions}/` (module + controller + service + dto, grouped in subfolders). The dashboard of the money is a feature of `transactions`, not a domain (ADR 0021).
- `src/modules/core/auth/` — `AuthModule`: `AuthProviderInterface` port (`AUTH_PROVIDER` token) and `OidcAuthProvider` (`openid-client`). The domain barrel exports the token, the types, `@Public()` / `@CurrentUser()` and, for `main.ts` only, `JwtAuthGuard` and `AuthTokensService`: inject `@Inject(AUTH_PROVIDER)`, never the provider class.
  - Login flow: `AuthController` (`GET /api/auth/login` → 302 to the IdP, `GET /api/auth/callback`) is HTTP only; `AuthService` ties the provider and `UsersService` together and touches the user last; `AuthChecksService` signs/verifies the cookie `coffra_oidc_checks` that carries `state`, `nonce` and the PKCE verifier between the two requests (signed with `AUTH_CHECKS_SECRET`, 10 min, single-use, `SameSite=Lax`; ADR 0009). The callback path is the redirect URI registered at the IdP: do not move it.
  - Session (ADR 0006, 0010): after the callback `AuthTokensService` (`core/auth/auth-tokens.service.ts`) issues the app's own access and refresh JWT, returned in the response body (`{ accessToken, refreshToken, expiresIn }`, `no-store`). Claims are only `sub` (`User.id`), `iat`, `exp`; each token has its own secret and HS256 is pinned. `POST /api/auth/refresh` (`{ refreshToken }`) checks that the user still exists and issues a new pair whose refresh token **inherits the old `exp`** (`JWT_REFRESH_TTL_SECONDS` = longest session from the login). `POST /api/auth/logout` changes nothing on the server and returns `{ endSessionUrl }` for the IdP session: the client drops the tokens and navigates the browser there. `verifyAccess` is for the guard, never `verifyRefresh`.
  - Access control (ADR 0011): `JwtAuthGuard` (`core/auth/jwt-auth.guard.ts`) is made global in `main.ts` (`app.useGlobalGuards(new JwtAuthGuard(app.get(Reflector), app.get(AuthTokensService)))`: built by hand, no provider, so the `core` barrel exports the guard and `AuthTokensService` for it) and **denies by default**: every route needs `Authorization: Bearer <access token>` unless it is `@Public()`. The guard only checks the token (signature, `exp`, claims), never the database, and sets `request.auth = { userId }`. A rejection is always `401 Invalid or expired access token` with `WWW-Authenticate: Bearer`. A public route does not read the header at all.
  - `@Public()` and `@CurrentUser()` (`core/auth/decorators/`, exported from the `core` barrel) are what other domains use: `@CurrentUser() userId: string` is the id from the token, only on routes that are not public (it throws on a public one). `@Public()` also clears the global bearer requirement of that operation in Swagger, so one decorator serves both. On `AuthController` it goes on each method, not on the class, so a route added there stays protected. The public surface is exactly `login`, `callback`, `refresh`, `logout` and `GET /api/health`; `test/modules/core/public-routes.spec.ts` pins that list, so a new public route means editing it on purpose.
  - An app booted without that `main.ts` line has no authentication (`configureApp` does not add it): a test or e2e bootstrap that needs the guard repeats that line itself.
  - A new endpoint needs nothing to be protected. Do not put `@UseGuards` or `@ApiBearerAuth()` on it: both are already global.
- `src/modules/core/users/` — `UsersModule`: `UsersService.upsertByExternalSubject` finds or creates the `User` by `(oidc, sub)` (never by email) and keeps the email in sync; `findById` serves the token refresh and `GET /api/users/me` (`UsersController`: `{ id, email }` of the token's user, 401 when it no longer exists). The service is exported to `AuthModule`, not through the domain barrel.
- `src/modules/core/ownership/` — `OwnershipModule` (ADR 0012): the one place that decides whose rows a request sees. `OwnershipService` runs no query; the domain spreads its pieces into its own Prisma calls, so a foreign row is never found and ends like a missing one (`404 <Resource> not found`, same body, never `403`). A domain module imports `OwnershipModule` from the `core` barrel, not `CoreModule` (that would boot auth), and injects `@Inject(OwnershipService)`.
  - `@CurrentOwner() owner: Owner` is for data (every route of `transactions`, the dashboard included); `@CurrentUser()` is for the identity of the caller only (`GET /api/users/me`). A domain service takes `owner: Owner`, never a `userId`, and never reads its fields: with workspaces the owner changes, the service signatures do not.
  - Usage (the review rule: **every** query on `account`, `category` and `transaction` spreads `ownership.scope(owner)`, writes included; `findUnique({ where: { id } })` in a domain is a red flag; the domain never writes `userId` into a `where` or `data` itself):

    ```ts
    this.prisma.account.findMany({ where: this.ownership.scope(owner) })
    const row = await this.prisma.account.findFirst({ where: { id, ...this.ownership.scope(owner) } })
    this.ownership.orNotFound(row, 'Account')
    this.prisma.account.create({ data: { ...fields, ...this.ownership.ownerData(owner) } })
    this.prisma.transaction.findMany({ where: { account: this.ownership.scope(owner), ...filters } }) // child model: through its parent
    ```

  - One owner per request: an account and a category are checked to belong together by reading both through the same scope.
  - `Account` and `Category` carry a nullable `tenantId` (always `NULL`, nothing writes or reads it). **Never return a Prisma row from a controller**: map it to a view type, otherwise `userId` and `tenantId` leak into the API.
  - `test/modules/core/ownership/foreign-equals-missing.spec.ts` proves the composition over HTTP; `test/modules/transactions/owner-scope.spec.ts` is a compile-time contract (`pnpm ts`) that the scope fits the `transactions` models. Through real queries, route by route, isolation is proven by the integration suite (`test/integration/isolation/`, ADR 0019).
- `src/modules/transactions/accounts/` — `AccountsModule` (imports `OwnershipModule`): `POST/GET/GET :id/PATCH/DELETE /api/accounts`, the reference CRUD for the rest of the domain (see CRUD conventions). `openingBalance` is a column, not a transaction; the currency is set on create only and a `PATCH` with `currency` is a 400 (ADR 0013). Deleting an account with transactions is a 409 decided by the `Restrict` of the database, not by a count beforehand.
  - Every response with an account carries `balance` (ADR 0018): `openingBalance` + income + transfer `in` − expense − transfer `out`, a four-decimal string in the account currency, **computed on read and never stored**. `AccountsService.totals` is one `transaction.groupBy` by `(accountId, type, transferDirection)` with `_sum.amount`, in the owner scope plus `accountId in (the accounts just read)` (the ids only narrow the query for the planner: without them it scans the whole table once there are many users). The list reads the accounts, then aggregates for all of them: two queries however many accounts there are; a new account is not aggregated (balance = opening balance). `balanceOf` (`accounts.balance.ts`) adds the sums in `Money` (`common/money.ts`: `Prisma.Decimal` with 40 digits, the default 20 rounds large sums silently); `toAccountView(row, balance)` formats it.
  - Only transactions dated up to `asOf` (inclusive) count, so a planned one does not move the balance yet; the opening balance always counts. `GET /api/accounts` and `GET /api/accounts/:id` take `?asOf=YYYY-MM-DD` (`BalanceQueryDto`); without it, and in the answers of `POST`/`PATCH`, the day is **today in UTC** (`formatIsoDate(new Date())`), like every date in the API, never the local day of the server. A client in another zone sends its own date.
  - A new way of reading transactions for a balance must keep the owner scope in the `where` (never `$queryRaw` with a hand-written `userId`).
- `src/modules/transactions/categories/` — `CategoriesModule` (imports `OwnershipModule`): `POST/GET/GET :id/PATCH/DELETE /api/categories`, the account pattern with one field (`name`). Names are trimmed, unique per owner and **case-sensitive** (`Food` and `food` are two categories); a duplicate on create or rename is a 409 from the unique constraint (`P2002`), never a lookup beforehand. A category that still has transactions cannot be deleted: a 409 from `Restrict` on `Transaction.category` (`P2003`), not a count (ADR 0014, which changed the `SetNull` of ADR 0004).
- `src/modules/transactions/transactions/` — `TransactionsFeatureModule` (not `TransactionsModule`: that is the domain module; imports `OwnershipModule`): `POST/GET :id/PATCH/DELETE /api/transactions` for income and expense. The account and the category of the body are read through the owner scope before the write (both at once, the account reported first): a foreign or missing one is `404 Account not found` / `404 Category not found`. A move to another account needs the same currency (`409` otherwise). A side of a transfer is returned by `GET` but is a `409` on `PATCH`/`DELETE` (it changes through `/api/transfers/{transferPairId}`), and every write carries `type in (income, expense)` in its `where` (ADR 0015).
  - `GET /api/transactions` (ADR 0016) lists both sides of a transfer too, filtered by `accountId`, `categoryId`, `type` and a range `from`/`to` (both inclusive), ordered by `(date, createdAt, id)` (`order=desc` default, `asc` flips all three), paged by a keyset cursor: `limit` (1–100, default 50), `cursor` = the `nextCursor` of the previous page, `{ items, nextCursor }` with `null` on the last page, no total. The cursor (`transactions.cursor.ts`) is base64url JSON of the sort key of the last returned row and the `order`: values, never a lookup by `id`, not signed, bound to `order` (`@IsListCursor()`, `decorators/`), not to the filters. The keyset goes into `AND`, never next to the `from`/`to` filter on `date`. The indexes `(accountId, date, createdAt, id)` and `(date, createdAt, id)` are there for these queries (measured, ADR 0016): a change of the order or the filters is a change of the indexes too.
- `src/modules/transactions/transfers/` — `TransfersModule` (imports `OwnershipModule`): `POST /api/transfers`, `PATCH/DELETE /api/transfers/:pairId` (ADR 0017). A transfer is the pair of `Transaction` rows (`out` on the source, `in` on the target) as one resource: `pairId` is their `transferPairId`, the response is `{ pairId, fromAccountId, toAccountId, amount, date, note }`. No `GET`: both sides come from `GET /api/transactions`. Every write touches both sides at once (`createManyAndReturn`, a batch `$transaction` with `out` first, `deleteMany`); amount, date and note are the same on both, held by the service only. `PATCH` changes the amount, the date, the note and the accounts (same currency as the transfer). **A transfer never has a category:** `categoryId` in the body is a `400`, even `null`. The same account on both sides is a `400` in one body (ids lower-cased by `@IsAccountId()`, so letter case does not hide it) and a `409` when a single account in a `PATCH` meets the side that stays; another currency is a `409`, a foreign account `404 Account not found`, a foreign or missing pair `404 Transfer not found`. A broken pair (not one `out` and one `in`) is a `500`, never a `404`.
- `src/modules/transactions/totals/` — `TotalsModule` (imports `OwnershipModule`): `TransactionTotalsService` (`categoryTotals(owner, { from, to })` and `dailyTotals(owner, { from, to })`), the only way to read the transactions as figures (ADR 0020, 0022): the dashboard of the domain injects it, and so would another domain. No route. It is exported from the `transactions` barrel with its types (`CategoryTotal`, `DayTotal`, `TotalsCategory`, `TotalsRange`) and `TransactionsModule` re-exports its module, so a domain that imports `TransactionsModule` can inject `@Inject(TransactionTotalsService)` (none does yet: the dashboard is inside the domain and imports `TotalsModule`); nothing else of the domain is exported (`transactions.module.spec.ts` pins both).
  - It returns `{ currency, category: { id, name } | null, income, expense }` per currency and category for the days `from`..`to` (both inclusive, `YYYY-MM-DD`, UTC; `from` after `to` is `[]`), ordered by currency, then by category name by code units (not `localeCompare`), `category: null` last. Transfers and the opening balance never count; a transaction dated in the future counts when its day is in the range: the service does not know today, the caller picks the days.
  - Three reads, however many accounts and categories there are: one `transaction.groupBy` by `(accountId, categoryId, type)` in the owner scope with `type in (income, expense)` and the range, then the currencies of the accounts and the names of the categories by the ids of the sums, each scoped. They are read **after** the sums (both foreign keys are `Restrict`, so what a sum refers to still exists). No `accountId in` in the aggregation: with the range in the filter the planner already uses the index (ADR 0020, measured). `foldGroups` (`totals/utils/fold-groups.ts`, pure) adds the groups of the accounts of one currency; every helper it uses is a function of its own in the same `totals/utils/` folder (`currency-of.ts`, `category-of.ts`, `row-key.ts`, `add-to-row.ts`, `compare-rows.ts`, `compare-text.ts`), one function per file, no barrel. That folder is local to `totals`; it is not `src/utils`, which holds the helpers of the whole app.
  - `dailyTotals` returns `{ currency, date, income, expense }` per currency and day (`date` is `YYYY-MM-DD`) for the same days and the same transactions as `categoryTotals`, ordered by currency, then by day; a day without a transaction has no row. Two reads: one `transaction.groupBy` by `(accountId, type, date)` and the currencies of the accounts it refers to (no category is read), the second after the sums for the same reason. **`incomeExpenseWhere` is the filter of both aggregations** (owner scope through the account, `type in (income, expense)`, the range): a new sum goes through it, so it cannot forget the scope or count a transfer. A `DATE` comes back from Prisma as midnight UTC and leaves through `formatIsoDate`, never a local getter. `foldDays` (`totals/utils/fold-days.ts`, with `compareDays`) adds the accounts of one currency in `Money`, from `new Money(0)`.
  - A sum whose account or category the scoped read did not return is an `Error`, never a name of a foreign category.
  - **The amounts are `Money` values** (`Prisma.Decimal` with 40 digits): a consumer adds and subtracts them as they are, or from its own `Money`, **never from `new Prisma.Decimal(0)`** (that rounds to 20 digits). A consumer's spec needs amounts of more than 20 digits.
- `src/modules/transactions/dashboard/` — `DashboardModule` (imports `TotalsModule`; no `OwnershipModule`, no `PrismaService`): `GET /api/dashboard?period=3m|6m|1y` (ADR 0021, 0022), the income and the expense of the last months per currency, category and month. A feature of `transactions`, not a domain of its own: it has no table and reads the transactions only through `TransactionTotalsService`, which carries the owner scope. Flat layout: `dashboard.{module,controller,service,mapper,types}.ts`, `constants.ts` (`PERIODS`, `DEFAULT_PERIOD`, `PERIOD_MONTHS`), `dto/`, and `utils/` (local to the feature, one function per file, no barrel).
  - **The window** (`utils/period-window.ts`): the last 3, 6 or 12 calendar months including the current one, from the first day of the oldest month to the last day of the current month, so a planned transaction later this month counts. It is plain integer arithmetic on `YYYY-MM-DD` (`day-in-month.ts`, `days-in-month.ts`): **no `Date`, so no time zone**. The one place the clock is read is `DashboardService.get`, `formatIsoDate(new Date())`: today in UTC, like every date in the API (a client east of UTC sees the old month between its midnight and UTC midnight, as with the balance). A spec of the window fakes only `Date` (`vi.useFakeTimers({ toFake: ['Date'] })`) and runs the service in the extreme time zones.
  - **The answer** is `{ period, from, to, currencies[] }` (`period` is the one used, `3m` by default; a value that is not offered or a repeated `period` is `400`; an unknown parameter is dropped by the global `whitelist`, so a misspelt `perod` counts as `3m`). Every currency has `income`, `expense`, `net`, `categories[]` (`categoryId`, `name`, `income`, `expense`, `net`) and `trend[]` (`month` as `YYYY-MM`, `income`, `expense`, `net`), the amounts four-decimal strings; the transactions without a category are the row with `categoryId: null` and `name: null`. Only currencies with a counted transaction, in the order of the totals service (alphabetical); no ratios or shares (the client divides). Transfers and the opening balance never count.
  - `summarizeTotals` adds the rows of a currency up and orders the categories by `income + expense`, largest first, the row without a category last, ties in the order of the totals service (`compareCategories`, a stable `toSorted`). The sums start from `new Money(0)` (from the `common/` of the domain), never from `new Prisma.Decimal(0)`; `toDashboardView` only writes the strings (`formatMoney`), so nothing is rounded before the end. Its specs need amounts of more than 20 digits across many categories.
  - **The trend** (ADR 0022) is one entry per calendar month of the window (UTC), the oldest first: exactly 3, 6 or 12, **a month without a transaction is there with zeros**, so the series never has gaps. The months come from `dailyTotals`: `foldMonths(days, windowMonths(window), currencies)` (`utils/`, pure, `Date`-free like the window; `monthIndex` is the month number shared with `periodWindow`) adds the days of each month in `Money` and writes the net. `DashboardService.get` reads the clock once, then asks `categoryTotals` and `dailyTotals` for the **same window** at once (`Promise.all`). The two are two reads, not one snapshot: the currencies are those of the categories, the days of any other currency are left out (a transaction written between the reads) and a currency without a day has zeros; a day outside the months is an `Error`. The months of a currency add up to its totals. `summarizeTotals(rows, trends)` attaches each series and fails for a currency that has none.
  - The isolation spec (`test/integration/isolation/dashboard.spec.ts`) fixes the clock to a day in February 2026: the seed is dated January 2026, and the window is counted from today. It signs new tokens after moving the clock (`issueToken`).
- `src/modules/transactions/common/` — what the features of `transactions` share: `constants.ts` (`MONEY_SCALE`, `SUM_PRECISION`, `SIGNED_DECIMAL_PATTERN`, `POSITIVE_DECIMAL_PATTERN`, `ISO_DATE_PATTERN`, `QUERY_INTEGER_PATTERN`, `RESOURCE_NAME_MAX_LENGTH`, `NOTE_MAX_LENGTH`), `formatMoney`, `Money` (`money.ts`), `decorators/` (`@IsDecimalAmount()`, `@IsPositiveDecimalAmount()`, `@IsIsoDate()` with its check `isIsoDate`, `@IsNotBefore()`, `@IsQueryInteger()`, `@IsResourceName()`, `@IsNote()`). Moves to `src/utils` once a second domain needs it.
- A feature inside a domain (`core/auth`, `core/users`, ...) is its own Nest module, `<feature>.module.ts`, imported by the domain module. The feature module is internal: only the domain's `index.ts` is public.
- Infrastructure modules (not domains): `src/modules/{config,health,prisma}/`, each with an `index.ts`.
- `src/utils/` — project-wide pure helpers (no Nest, no domain imports), one function per file, the file is the kebab-case of the function name (`stringOrUndefined` → `string-or-undefined.ts`, the shared ESLint enforces kebab-case filenames), all re-exported from the `index.ts` barrel and imported through it (`'../../../utils'`). Put a helper here once a second domain needs it, or when it is generic by nature.

## Module boundaries

Modular monolith: one Nest app, a domain = a module in `src/modules/<domain>/`.

1. A domain exports only through its `index.ts`. Everything else imports `'../<domain>'`, never `'../<domain>/…'`.
2. A domain touches only its own Prisma models (`prisma/schema/<domain>.prisma`). Foreign data comes through a public service of the other domain.
3. Dependency direction is `core` ← `transactions`. `core` imports no domain, `transactions` only `core`.
4. The only allowed relations between schemas are foreign keys to `User` and `tenantId`.

- **No rule is lint-enforced** (deliberately dropped): the boundaries hold by discipline and review. Inside its own domain, files import freely.
- `config`, `health` and `prisma` are infrastructure: reachable from anywhere through their `index.ts`, but they import no domain. **One exception:** `health` imports `Public` from the `core` barrel (`'../core'`) so the probes need no token (ADR 0011). `core` never imports `health`, so there is no cycle.
- Adding a domain: folder + `<domain>.module.ts` + `index.ts`, an import in `AppModule`.

## Architecture decisions

Significant architectural decisions are written as separate markdown files in `docs/decisions/`, one per
decision, named `NNNN-kebab-title.md` (next free number). Format and the index are in
`docs/decisions/README.md`. The point is that a developer (or an AI agent) debugging or changing the
code later can see **why** something was built that way, not only what it does.

- **Read first:** when debugging, or when a design looks odd (a CHECK constraint, a pinned dependency, a missing `userId`, a module boundary), look in `docs/decisions/` for the reason before changing it.
- Write one when you pick between real alternatives with lasting consequences (module boundaries, data model, auth/session, a dependency pinned for a structural reason). Not for routine implementation choices.
- Record the context, the alternatives you rejected and the consequences, not only the outcome.
- Write it in the same PR as the change, and add it to the index.
- Do not rewrite an accepted decision. To change course, add a new record and mark the old one `Superseded by NNNN`.

## CRUD conventions

Set by `transactions/accounts` (T14); categories, transactions and transfers follow them.

- **Layout:** `<feature>/` with `<feature>.module.ts`, `<feature>.controller.ts`, `<feature>.service.ts`, `<feature>.types.ts` (`<Model>View`, `Create<Model>Input`, `Update<Model>Input`), `<feature>.mapper.ts` (`to<Model>View`) and `dto/` (`<model>.dto.ts` for Swagger, `create-<model>.dto.ts`, `update-<model>.dto.ts`). The controller only passes `@CurrentOwner() owner: Owner` and the DTO on; the service takes `owner` and an input type (the DTO `implements` it).
- **Status codes:** `POST` `201` with the resource, `GET` `200`, `PATCH` `200` with the whole resource, `DELETE` `204` with no body (`@HttpCode(HttpStatus.NO_CONTENT)`). `400` for invalid input, including an id in the path that is not a UUID (`@Param('id', ParseUUIDPipe)` on every `:id`, `@Param('pairId', ParseUUIDPipe)` on the `:pairId` of a transfer: any well-formed UUID goes on to the lookup, so the database never sees a malformed one). `404` for a missing **or** foreign id, only through `ownership.orNotFound`, in the path and in the body alike (`404 Account not found` for an `accountId` the owner does not have). `409` for a conflict of state (`Restrict`, a unique constraint, a domain rule). The rule behind them (ADR 0015): `400` when the request alone decides, `404` for an id the owner does not have, `409` when a valid request conflicts with what is stored. The guard answers `401` before any pipe runs.
- **Responses:** always a `<Model>View` built by the mapper in `<feature>.mapper.ts` (`toAccountView`: a pure function, no DI, listed fields only, with its own spec), never a Prisma row (`userId`, `tenantId`, timestamps stay inside). Swagger documents every response code of the operation.
- **Money:** in as a decimal string through `@IsDecimalAmount()` (a JSON number, an exponent, more than 4 decimal places or more than 15 integer digits is a `400`, so nothing overflows `Decimal(19,4)` into a `500`); out through `formatMoney` with exactly four decimal places. Prisma takes the string as it is. An amount whose sign comes from elsewhere (`Transaction.amount`, CHECK `amount > 0`) uses `@IsPositiveDecimalAmount()`, which also refuses every spelling of zero.
- **Dates** (`@db.Date`): in as `YYYY-MM-DD` through `@IsIsoDate()` (a day that exists, years 0001–9999), to Prisma through `parseIsoDate` (midnight UTC), out through `formatIsoDate` (UTC), both from `src/utils`. Never `new Date(year, month, day)`, `Date.UTC` or the local getters (`getDate()`, ...): the driver adapter writes the UTC date part, so local time moves the day by one depending on the time zone of the server. A spec of a date runs in several zones (`test/utils/use-time-zone.ts`). A range of days is `from`/`to`, both inclusive, `@IsNotBefore('from')` on `to` (a `400`); `lte` at midnight UTC of `to` keeps that whole day only because the column is a `DATE`. A `TIMESTAMP` (`createdAt`) travels through the adapter in UTC to the millisecond too (verified in three zones, ADR 0016): out through `toISOString()`, in through `new Date(iso)` of exactly that spelling.
- **Validation before the database:** every CHECK constraint has a DTO rule that fires first (the currency regex is the one of `currency_iso`), so a constraint is a last line of defence, never the answer to a client.
- **Names:** `@IsResourceName()` (trimmed, non-empty, at most 100 characters).
- **Optional fields and `null`:** an optional field of a create DTO uses `@ValidateIf((_dto, value) => value !== undefined)`, not `@IsOptional()` (that lets `null` through to a NOT NULL column, a `500`). The update DTO is `PartialType(CreateDto, { skipNullProperties: false })` for the same reason. `null` is accepted only for a nullable column, explicitly. A field that must not change is declared on the update DTO only to be refused (`@Equals(undefined, …)` + `@ApiHideProperty()`): the global `whitelist` would otherwise drop it silently and answer `200`.
- **Prisma `data` from optional input:** `omitUndefined({ … })` (`src/utils`), because `exactOptionalPropertyTypes` does not accept an explicit `undefined`. List the fields by name; never spread a DTO into `data`.
- **Prisma errors** are mapped in the service, where the meaning of the code for that operation is known: `isPrismaError(error, PrismaErrorCode.X)` from the `prisma` barrel (`P2003` is a `409` on deleting an account or a category with transactions but a `401` on creating one for a deleted user; `P2002` of a unique constraint is a `409`; `P2025` after a scoped read is the same `404`). Anything else is rethrown and ends as a `500` in the log. No global exception filter. With `@prisma/adapter-pg` both a foreign key violation (`P2003`) and a unique violation (`P2002`) arrive as `PrismaClientKnownRequestError` (verified against the dev Postgres). Do not read `meta.target`: its shape differs between driver adapters.
- **The database decides conflicts:** a unique name or a `Restrict` is not checked by a query beforehand (that races with a parallel request and costs a query); the write fails and the service maps the code. Both foreign keys of `Transaction` are `Restrict`, so a cleanup deletes transactions before categories and accounts.
- **Reads before writes:** `update`/`delete` first run the scoped read (`findOwned`: `findFirst` + `orNotFound`), then write with the scope again (`where: { id, ...scope }`). Exception: a delete with nothing to decide but existence may be one scoped `deleteMany` whose `count` gives the `404` (the transfer).
- **Writes of several rows** (the two sides of a transfer) go in one statement (`createManyAndReturn`, `deleteMany`) or in one batch `$transaction([…])` in a fixed order, never as separate `await`s: a failure in between would leave half of the change. A mock cannot prove it; `test/integration/transfers/atomicity.spec.ts` does, against Postgres (ADR 0017, 0019).
- **Ids compared in code** are lower case. Postgres finds a `uuid` in any letter case and `@IsUUID()` accepts upper case, so an id that the code compares as a string (two accounts that must differ) is lower-cased on input (`@IsAccountId()`, `transfers/decorators/`).
- **References in the body** (an `accountId`, a `categoryId`) are read through the same scope before the write, because the database cannot tell whose they are: in parallel, reported in a fixed order. That check is safe only for what never changes (the owner, the currency of an account); a reference deleted in between fails the foreign key (`P2003`), and the service reads the references again to answer the same `404`.
- **Lists:** a stable order (a unique tie-breaker such as `id` after the sort column). A list that pages uses a keyset cursor, never an offset (ADR 0016): read `limit + 1` rows, make `nextCursor` from the last row returned, put the sort key values in the cursor and never look a row up by an id from it. An id in a filter is a predicate, not a reference: a foreign or missing one gives an empty page (`200`), not a `404`. A query DTO may use `@IsOptional()` (a query string has no `null`); a whole number in a query goes through `@IsQueryInteger()` (the global pipe does not convert, and `Number()` is too lenient); a repeated parameter arrives as a list and fails validation; an unknown one is dropped by the global `whitelist`, so a misspelt filter lists unfiltered.
- **Tests:** the service over a mocked Prisma and the real `OwnershipService` (pins the `where`, the `data` and the error mapping); the controller behind the real guard and `configureApp` with a mocked service (status codes, validation table with `it.each`, the owner from the token, the body cannot choose the owner). The controller boot is shared: `useControllerApp(Controller, Service, mock)` in `test/modules/transactions/use-controller-app.ts` (returns `send`, `anonymous`, `calls`), the folder's `setup.ts` keeps only the mock and the fixtures; `prismaError(code)` is in `test/modules/transactions/prisma-error.ts`. Isolation through real queries, the atomicity of writes of several rows and what the driver adapter does with dates and sums belong to the integration suite (see Conventions → Integration specs). A DTO field declared only to be refused (`categoryId?: never`) is an own `undefined` of every instance: a controller spec leaves it out before `toStrictEqual`.

## Conventions

- One module per feature; keep controllers thin, logic in services (DI).
- **Swagger decorators sit apart from the functional ones**, on a class and on a method alike: first what changes behaviour (`@Controller`, the route, `@HttpCode`, `@Header`, `@Redirect`, `@Public()`, `@HealthCheck()`), then a `// Swagger` comment line, then only documentation (`@ApiTags`, `@ApiOperation`, `@Api…Response`, `@ApiParam`). Everything below `// Swagger` can be removed without changing what the API does. A decorator that does both (`@Public()`) counts as functional. Nest and Swagger do not depend on the order.

  ```ts
  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  // Swagger
  @ApiOperation({ summary: 'Delete an account that has no transactions' })
  @ApiNoContentResponse({ description: 'Deleted' })
  remove(…) {}
  ```

- **Comments are JSDoc on declarations, `//` only inside a body** (and the `// Swagger` separator). The rules (the blocks, `@param name - …`, `@property`, `@throws`) are in the `coding-conventions` skill, `references/nestjs.md` → JSDoc. The model in this app: `transactions/accounts/accounts.service.ts`.
- DTOs validated with `class-validator`; enable a global `ValidationPipe` when adding input.
- All routes live under the `api` prefix. New endpoint tests must boot via `configureApp(app)`.
- **Ports get the `Interface` suffix** (`AuthProviderInterface`): an interface that classes implement and callers depend on. Plain data shapes (`AuthSession`, `LoginRequest`) do not.
- **Tests mirror `src/`**: module tests in `test/modules/<module>/…` (plus the feature folder when the module has one, e.g. `test/modules/core/auth/`), util tests in `test/utils/`, tests of root files (`app.setup.ts`, `swagger.setup.ts`) directly in `test/`.
- **One spec file per use case** for a controller, service or provider: a folder named after the source file (`auth.service.ts` → `test/modules/core/auth/auth.service/`) holds `<use-case>.spec.ts` in kebab-case (`complete-login.spec.ts`, `refresh.spec.ts`; a controller by endpoint: `login.spec.ts`, `callback.spec.ts`), `dependency-injection.spec.ts` for the `@Inject` check, and a `setup.ts` with the fixtures and a `use<Subject>()` function that registers the `beforeEach`/`afterEach` of the block it is called in and returns the mocks. Helpers shared by several folders sit next to them (`auth/use-quiet-warnings.ts`). A small file with one subject and one use case stays a plain `<subject>.spec.ts` (`env.validation.spec.ts`, a util). `setup.ts` and the helpers are not `*.spec.ts`, so vitest does not run them, and `eslint.config.mjs` allows devDependencies in all of `test/`.
- A spec that mocks a module (`vi.mock('openid-client', …)`) repeats the `vi.mock` call in every file: it is hoisted per file and cannot live in `setup.ts`.
- **Specs need no `.env`.** `vitest.config.mjs` (`test.env`) sets a complete dummy environment for the whole run, because importing anything from `src/modules/config` validates the environment at once. `process.env` wins over a developer's `.env`, so the run is the same on every machine and in CI. A new required variable in `env.validation.ts` needs a value there too. A spec that needs other values stubs them (`vi.stubEnv`) before the import.
- **Two vitest projects, few workers.** `unit` (everything outside `test/e2e/`, 2 workers) runs first, then `e2e` (`test/e2e/**`, one file at a time). The specs open many short-lived loopback connections (supertest, the fake IdP); with more parallelism, connection setup on some Windows machines stalls in steps of 10 s and specs fail on timeouts that have nothing to do with the code. Do not raise `maxWorkers` or turn `fileParallelism` back on without checking that on such a machine. `pnpm test:e2e` / `pnpm test:unit` runs one project. The integration suite is not a project of this config: it has its own (below), so `pnpm test` never needs a database.
- **E2E specs** live in `test/e2e/<area>/` (`test/e2e/auth/`), their shared support in `test/e2e/support/`. `useAuthApp()` (`test/e2e/auth/setup.ts`) boots the real `AppModule` against a fake OpenID provider (`FakeIdp`: `node:http` on `127.0.0.1`, random port, RS256 ID tokens signed through `@nestjs/jwt`) and an in-memory user table (`InMemoryPrisma` stands in for `PrismaService`, the real `UsersService` runs on it). The real `OidcAuthProvider` and `openid-client` run unmodified, so this is where `state`, `nonce`, PKCE, `iss` and `aud` are proven to be enforced, which the unit specs (they mock `openid-client`) only pin as arguments. No Docker, no `.env`, no fixed port. Rules for a new e2e spec:
  - Set the environment with `vi.stubEnv` and import everything that reaches `modules/config` **dynamically, afterwards** (`loadApp()`): `ConfigModule.forRoot` validates the environment when `config.module.ts` is first imported, so a static import is too early. Dynamic imports need the `.js` extension (`"module": "node20"`).
  - Every e2e bootstrap repeats the `app.useGlobalGuards(...)` line of `main.ts` and asserts a `401` on a protected route (`protected-routes.spec.ts`, ADR 0011).
  - `travel(seconds)` moves `Date` only. The fake IdP shares the process clock, so sign first and travel after; an expired ID token is made with an explicit `exp`.
  - A refusal asserts the reason in the log (`warn`), not only the status, and has a control that succeeds with the same setup: a broken fake IdP also answers `401`.
- **Integration specs** (`pnpm test:integration`, ADR 0019) live in `test/integration/<area>/` (`isolation/`, `transfers/`, `dates/`, `balances/`, `dashboard/`), their support in `test/integration/support/`, their config in `test/integration/vitest.config.mjs` (one worker, one file at a time). They run the real `AppModule` and the real `PrismaService` against a throwaway database on a Postgres server: `TEST_DATABASE_URL`, by default `postgresql://coffra:coffra@127.0.0.1:5439/coffra_test` on the dev Postgres (`test/integration/database-url.mjs`, the one place of that default). `pretest:integration` (`test/integration/require-postgres.mjs`) first tries one TCP connection there and, when nothing listens, tells you to run `pnpm infra:up` and stops before vitest starts. The global setup recreates and migrates it (`prisma migrate deploy`) once per run and drops it afterwards; a database whose name does not start with `coffra_test` is refused, because the specs truncate every table. The suite never reads `.env`. Rules for a new integration spec:
  - `useIntegrationApp()` (`support/use-integration-app.ts`) boots the app once per file and, before every test, truncates the tables and seeds `world()`: users `a` and `b` with the same accounts, categories, transactions and transfer (`support/world.ts`; the amounts of `b` are a thousand times those of `a`). `as(persona)` sends with its token, `anonymous()` without; every file asserts one `401`.
  - A foreign id goes through `expectNotFound(send, foreignId, message)`: the same `404` and body as an id nobody has, and no write. Anything else a refusal must not change goes through `unchanged(…)` (every table before and after).
  - Every case has a control that succeeds for the owner with the same data. A test fails when anything is logged as an error (an unexpected `500`), unless it calls `expectErrors()`.
  - A new protected route needs a `describe('<METHOD> <path>', …)` in an isolation spec: `isolation/route-coverage.spec.ts` lists the routes from the router and fails otherwise. A route without data of an owner goes on its exception list, on purpose.
  - Requests go one at a time; only the specs of concurrent writes send two at once. A spec that moves the clock (`vi.useFakeTimers({ toFake: ['Date'] })`) signs a new token with `issueToken` afterwards; the hooks restore the clock and the time zone.
  - Not provable here: the second owner scope of a write after a scoped read and the scope of the balance aggregation (the read before answers `404`, the owner never changes), and the scope of `readCurrencies` in the totals service (its ids come from sums that already carry the scope). The unit specs of the services pin them.
  - **The dashboard is proven against an independent SQL** (`dashboard/`). `sqlDashboard(prisma, userId, { day, period })` (`support/dashboard-sql.ts`) works out the window with `date_trunc` and the months with `generate_series`, so it shares no arithmetic with `periodWindow` or `foldMonths`; `date_trunc` and `generate_series` over a `date` follow the time zone of the connection, so everything is cast to `timestamp`, and currencies and names are ordered `COLLATE "C"` (code units, like the service). `seedLedger(prisma, persona, { seed, scale })` (`support/ledger.ts`) gives a persona about 1 650 rows from 2024 to mid 2029 from a generator with a fixed seed (a USD account, a second EUR account, four more categories, transfers, rows without a category, the first and the last day of every month); the second user's amounts are ×1000. `stopClock(instant, world, issueToken)` (`support/clock.ts`) stops `Date` and signs new tokens. `matches-sql.spec.ts` compares every period on seven clocks for both users; `rules`, `boundaries` and `precision` write a few rows with `clearTransactions` + `writeRows` and compare with numbers worked out by hand, so a rule that the API and the SQL got wrong the same way is still caught; `time-zones.spec.ts` runs the server in UTC+14 and UTC−11. A comparison first checks that it is not comparing two empty answers (`expectNotEmpty`) and that the answer adds up (`expectConsistent`, in ten-thousandths as `BigInt`).
  - A transaction that points to a category of another user cannot be made through the API (a `404`), but the database allows it. `isolation/dashboard.spec.ts` writes it through Prisma and expects a `500` that does not contain the name of that category.
- `openid-client` does not verify the ID token signature in the code flow (the token comes straight from the token endpoint over TLS: OIDC Core 3.1.3.7 step 6). That is why an `https:` issuer is mandatory in production, and why no spec can test a forged ID token signature.
- **Type files hold types only.** A module with its own types names the file `<module>.types.ts` (`core/users/users.types.ts`); a feature folder whose types are shared by several files (`core/auth/types.ts`) uses plain `types.ts`. Runtime values (DI tokens, cookie names, metadata keys, numeric limits) live in a plain `constants.ts` inside a feature folder (`core/auth/constants.ts`, `transactions/transactions/constants.ts`, `transactions/accounts/constants.ts`), even when one file only uses them: never `<feature>.constants.ts` there. `<module>.constants.ts` is only for an infrastructure module that is the whole folder (`prisma/prisma.constants.ts`).
- **Inject with `@Inject(Token)` on every constructor parameter.** Vitest (esbuild) emits no decorator metadata, so type-based injection resolves to `undefined` in `Test.createTestingModule`.
- `@nestjs/terminus` is pinned to 11.x: 12.x is ESM-only and this app is CommonJS.
- `openid-client` 6.x is ESM-only too and loads through `require(esm)`: that needs `"module": "node20"` in this app's `tsconfig.json` (otherwise TS1479) and Node >= 22.12. See ADR 0008.
- `OIDC_ISSUER_URL` over plain `http:` works outside production only (dev Keycloak). A production start with it fails env validation, so `pnpm start` (`NODE_ENV=production`) needs an `https:` issuer.
- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` and `AUTH_CHECKS_SECRET` must all differ (env validation enforces it), so one kind of signed value is never accepted as another. In production `OIDC_REDIRECT_URI` must be `https:` too (the login cookie is `Secure`).
- Run: `pnpm dev` (watch), `pnpm build`, `pnpm test`, `pnpm lint`; `pnpm test:integration` needs Postgres (`pnpm infra:up`); `pnpm test:image` needs Docker, the image (`pnpm image:build`) and Postgres.

## Dev environment (Postgres + Keycloak)

`docker/docker-compose.yaml` (project `coffra-dev`). **DEV ONLY — all credentials are public.**

```
pnpm infra:up      # postgres + keycloak, waits for healthchecks (Keycloak cold start ~30 s)
pnpm infra:down    # stops containers; Postgres data stays on volume `coffra-pgdata`
pnpm infra:logs
```

- Never run `docker compose down -v` — it deletes `coffra-pgdata` (the dev database).
- `pnpm dev` does not start Docker; run `infra:up` first. Ports bind to `127.0.0.1` only.
- Postgres: `localhost:5439`, user/password `coffra`, DB `coffra_dev` (= `DATABASE_URL` in `.env.example`). `pnpm test:integration` creates and drops its own database `coffra_test` on the same server and never touches `coffra_dev`; `docker compose -f docker/docker-compose.yaml up -d --wait postgres` starts Postgres alone, without Keycloak.
- Keycloak: `http://localhost:8080`, admin console `admin` / `admin`. Realm `coffra`, client `coffra-be`
  (confidential, secret `coffra-dev-secret`, PKCE S256 enforced, redirect `http://localhost:3000/api/auth/callback`).
  Login user `dev@coffra.local` / `dev`; its `sub` is fixed (`dde84b4e-…`), so `User.externalSubject` survives recreation.
- Keycloak keeps **no state** (embedded H2, no volume). `docker/keycloak/coffra-realm.json` is the single source of truth,
  imported on container creation only. After editing it: `docker compose -f docker/docker-compose.yaml up -d --force-recreate keycloak`
  (a plain `restart` keeps the already imported realm).
- To capture changes made in the admin console: `docker compose -f docker/docker-compose.yaml exec keycloak /opt/keycloak/bin/kc.sh export --realm coffra --file /tmp/r.json`,
  `docker compose … cp keycloak:/tmp/r.json …`, then prettier-format and commit.
- `iss` must equal `OIDC_ISSUER_URL` exactly (`KC_HOSTNAME` is pinned to `http://localhost:8080`). The app runs on the host, not in a container.
- A real IdP (homelab Keycloak) only needs the `OIDC_*` env vars changed plus an equivalent client (confidential, PKCE S256, matching redirect URI).

## Container image

The image is built from `docker/node/prisma/Dockerfile` (ADR 0023), a Dockerfile for any NestJS app with Prisma 7 in the workspace; this app is `--build-arg APP=coffra-be`. The build context is the repository root. It is not for Prisma 6 and older (the query engine binary).

```
pnpm image:build     # docker build -f ../../docker/node/prisma/Dockerfile --build-arg APP=coffra-be -t coffra-be:local ../..
pnpm test:image      # the image against the dev Postgres (needs Docker and `pnpm infra:up`)
```

- **No configuration or secret in the image.** The only baked variables are `NODE_ENV=production` and `PORT` (3000, build argument `PORT`), so the container needs the variables of `.env.example` at run time and, like any production start, an `https:` `OIDC_ISSUER_URL` and `OIDC_REDIRECT_URI` (discovery is lazy: any `https:` address starts it). No `TZ`: UTC, like the API.
- **Migrations are a second command of the same image, never part of the start:** `node node_modules/prisma/build/index.js migrate deploy` in `/app/apps/coffra-be`. That is why `prisma` is in `dependencies`. The schema engine it needs is fetched by the install script of `@prisma/engines`, which the production-dependencies stage runs on its own (the install itself runs without scripts: the `postinstall` of the app generates the client and needs the schema).
- **The runtime holds only** `build/`, `node_modules/`, `package.json`, `prisma/` and `prisma.config.ts`. A file the running app or the migrations need has to be copied into the runtime stage on purpose; `test/image/runtime-shape.spec.ts` pins that list.
- **The `HEALTHCHECK` runs `node` against `GET /api/health`** (503 when the database is down). Docker and Portainer use it, k3s ignores it. The main process is `node build/main`, so Node is PID 1 and gets SIGTERM; without `enableShutdownHooks` in `configureApp` the container would be killed after the grace period.
- **The production dependencies come from `pnpm deploy`** after the dependencies of the workspace root are dropped from the manifest (pnpm adds them to every install otherwise; 272 packages instead of 969). A new production dependency needs nothing in the Dockerfile.
- **Image suite** (`test/image/`, config `test/image/vitest.config.mjs`, not part of `pnpm test`): the global setup creates `coffra_test_image` on the server of `TEST_DATABASE_URL`, runs the migrations with the image itself and removes every container labelled `coffra-image-test` at the start and the end. `IMAGE` names another image than `coffra-be:local`. A new required variable in `env.validation.ts` needs a value in `productionEnvironment` (`test/image/support/environment.ts`) as well. The linter rewrites `http://` to `https://` in a string (except `localhost`): a case about plain http uses `localhost`.
